# Per-user configuration

Host and project mappings belong to the current user's `~/.config/remote-agent/`, independent of the code checkout. Mapping consumers live in `remote-agent.py`, `remote-agent-worker.py`, and `deploy.py`. The generic `periodic-checks.ts` extension discovers projects independently of these maps. See [mapping setup and deployment](../../README.md#mapping-setup).

## What it must do

- [x] Controller and worker read `remote-hosts.json` and `remote-projects.json` from `~/.config/remote-agent/`; missing user maps fail explicitly without consulting code-directory copies. Asserted by `ConfigurationTests`.
- [x] Project listing, sync, fetch, launch, and clipboard operations work with isolated user mappings and explicit/default host selection. Asserted by targeted `ControllerTests`, `SyncTests`, and `WorkerTests`.
- [x] Deployment sends local user mapping bytes to the selected remote user's `~/.config/remote-agent/`, with directory mode `0700` and file modes `0600`, including replacement of existing public permissions. Fresh deployed code directories contain neither map. Asserted by `DeployTests`.
- [x] Optional host `deploy_users` lists existing Unix usernames for deployment after the default SSH account, in configured order, through existing `authsudo` authorization. No account discovery. Homes resolve through the remote account directory; each target uses an isolated account environment. The same code payload/revision is deployed while both existing target maps remain byte-for-byte unchanged; missing maps or failed user deployments fail explicitly without copying operator maps. Wrapped/Windows cross-user deployments are rejected; absent/empty lists retain default deployment behavior. No service/session restart or saved-conversation modification. Asserted by subprocess fixtures in `tests/test_deploy_users.py`; real UID/authsudo acceptance remains a live verification responsibility.
- [x] Optional selected-host `build_host_scripts` is passed unchanged as `BUILD_HOST_SCRIPTS` to launched and restarted agents through tmux. An absent setting injects no value or personal fallback; an inherited caller value remains unchanged. Asserted by `WorkerTests.test_build_scripts_*`.
- [x] Deployment installs the generic periodic extension at user level without bundling project checklists. Worker launch and restart add no explicit extension arguments. Asserted by `DeployTests` and `WorkerTests.test_user_extension_*`.
- [x] Periodic checks opt in through ignored, host-private `periodic-checks.md` at the current Git project root, without host or project mappings. Each host maintains its own file; deployment never copies it. An absent file means no timer. Asserted by scheduler runtime and deployment tests.
- [x] Google OKF YAML frontmatter requires a nonempty string `type` and custom positive safe-integer `interval_seconds` within 1–2147483 seconds; unknown fields are allowed. Missing, malformed, or invalid metadata raises an explicit error and disables the timer, with no fixed 30-minute fallback. Asserted by scheduler metadata tests.
- [x] Metadata is read on `session_start`/reload; the first tick waits the full configured interval. Metadata edits require another start/reload; ticks do not reread metadata. Asserted by scheduler runtime tests.

- [x] `/periodic-checks status` (and no-argument `/periodic-checks`) reports `armed` or `disabled`, the checklist path when known, active `interval_seconds` and a relative schedule estimate when armed, or the disabled reason otherwise. Armed output uses `Next run: in N minutes`, singular `Next run: in 1 minute`, or `Next run: in less than a minute`, computed from the stored scheduled tick minus the current time at status invocation. Minutes round up at or above 60 seconds (90 seconds shows 2 minutes); due or overdue ticks use the subminute phrase. No absolute date or timezone is displayed. Arguments other than `status`, `run`, or no argument produce `Usage: /periodic-checks status|run`. Status displays its notification immediately even while main is busy or has pending messages, without aborting main, starting a model turn, triggering an audit, resetting the timer, or applying metadata edits. The relative estimate remains the scheduled boundary; skipped ticks advance it independently of child completion. Asserted by isolated scheduler command/dispatch tests and installed-Pi busy model/tool PTY tests.
- [x] `/periodic-checks run` requests the same direct read-only audit child immediately, including while main is busy or has pending messages, without resetting or advancing the scheduled countdown, rereading metadata, or re-arming a disabled schedule. Pending spawn/live audit gates refuse duplicates. Disabled schedules, missing/removed checklists, unavailable runtime/tools, and changed session/project identity produce reason-bearing warnings. Checklist removal stops the timer even during a pending spawn. Manual requests report `Periodic audit starting` before dispatch settlement, then `Periodic audit started` only for a non-error tool result with `details.dispatched: true`; blocked, undispatched, rejected, or error results produce contextual `spawn_agent` diagnostics, never false success. The command waits for neither spawn settlement nor child completion; `started` denotes accepted dispatch, not completed findings. Asserted by isolated scheduler dispatch fixtures and installed-Pi manual-run PTY tests.
- [x] Existing Pi sessions require reload (or a new session) to discover the newly installed command. Scheduled audits call `pi.callTool("spawn_agent", ...)` directly with a fresh-context `explore` child named `periodic-checks-audit`; busy main and pending messages do not skip dispatch. No follow-up/steering message or queued model prompt asks main to spawn the child. Asserted by isolated scheduler dispatch tests; command discovery requires extension loading.
- [x] Pending spawn calls suppress overlap until settlement, including rejection or unsuccessful dispatch; failures notify explicitly. A stored child named `periodic-checks-audit` suppresses overlap until `completed`, `failed`, or `aborted`, including restored children after reload. Unrelated children do not block dispatch. Child termination permits the next scheduled tick, not immediate dispatch; main `agent_end` does not release overlap. Reload/shutdown/replacement fence late spawn results from new pending locks and diagnostics. Asserted by isolated scheduler dispatch tests.
- [x] Audit instructions require rereading the host-private checklist, reporting only its requested scope, and confirming findings delivery to the originating main session. No corrections, nested spawning, builds, cleanup, blocking, cancellation, steering, edits, or deployment. See [audit behavior](../../README.md#optional-periodic-checks).

## Shared Claude credential ownership

- [x] Named accounts use only `~/.config/pi-claude-bridge/profiles/NAME/.credentials.json`; listing reads canonical directories. Native Claude launches use the selected canonical `CLAUDE_CONFIG_DIR` and remove inherited API/OAuth token overrides. Pi keeps caller credential environment. New launches require a selected owned account with a nonempty OAuth access token; no global fallback. Existing sessions remain untouched.
- [x] Account selection changes only `~/.claude/.active-profile`. Switching never copies or writes back grants. No worker action clears a selection, so a retained legacy global grant cannot become the native launch credential. Deleted/empty canonical credentials remain cleared regardless of legacy global/named credentials.
- [x] Bridge prepares legacy profiles before activation and owns migration. Workers require `.credential-owner` containing `shared-v1\n`; initialization takes an exclusive `.credential-migration` directory lock and never removes a preexisting lock. Explicit named login creates or claims its canonical directory with mode `0700` and marker, including preexisting unmarked directories with missing/empty/invalid credentials; it preserves canonical bytes until native login and never imports legacy grants. Invalid existing ownership markers and symlink profile directories fail explicitly; existing owned directories permit reauthentication.
- [x] `claude-account --login NAME` validates/prepares through the JSON worker, runs SSH worker `--claude-login NAME` directly in canonical config, and selects NAME only after successful authentication and nonempty token validation. Failure preserves old selection and other account grants. No global staging/release step.
- [x] Explicit `--name-current NAME` imports only an unnamed global login with a nonempty OAuth access token, moving it once into a previously absent private canonical directory with marker; existing/cleared accounts cannot be overwritten. See [shared accounts](../../README.md#shared-claude-accounts). Asserted by local subprocess fixtures in `tests/test_claude_account_freshness.py` and controller protocol tests; no real authentication, migration/deploy, or live harness proof is claimed.

## Implementation inventory

- `remote-agent.py` — controller host and project mapping consumption.
- `remote-agent-worker.py` — worker mapping consumption and selected-host agent environment.
- `deploy.py` — separate code archive and private mapping transfer.
- `periodic-checks.ts` — Git-root checklist discovery, bounded metadata scheduling, read-only scheduler status, and immediate manual audit dispatch, using Pi's exported YAML `parseFrontmatter` without a new dependency.

## Tests asserting this spec

- `tests/test_deploy_users.py` — real local subprocesses with fixture SSH/authsudo/account lookup: stale target worker upgrade followed by saved-history export, isolated target environment, unchanged maps and saved state, default-only behavior, missing-map/account/authorization failures, and unsupported transport rejection. No real UID switch or live deployment.

- `tests/test_remote_agent.py` — isolated configuration, selected controller/sync/worker behavior, real-tmux host environment propagation, and local execution of deployed payload.
- `tests/test_periodic_scheduler.mjs` — isolated extension scheduling, OKF metadata validation, full-interval timing, start/reload metadata changes, Git-root/checklist discovery, unmapped-project participation, read-only status output and argument validation, and checklist removal while busy; also exercised from deployed code. `tests/periodic_scheduler_dispatch.mjs` supplies isolated direct-dispatch, immediate busy-status, busy/pending manual runs, unchanged scheduled deadlines, manual refusal/acceptance feedback, overlap lifecycle, spawn-error, and late-result fencing fixtures. Native Node execution requires the installed Pi npm package to be resolvable, including through `NODE_PATH` for compiled-only Pi installations. See the [canonical test command and prerequisites](../../README.md#tests).

- `tests/test_periodic_runtime.py` with `tests/fixtures/periodic-runtime-provider.ts` — offline installed-Pi PTY proof during held model/tool turns: immediate visible status, direct scheduled/manual child dispatch, successful durable findings delivery before main release, duplicate refusal, unchanged regular countdown, and normal main completion. Main consumes its mailbox after becoming idle. Private test state and faux-provider requests do not use credentials or external provider networks.
